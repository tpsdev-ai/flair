- **A Memory row refused because it was locked is re-offered on a later sync once its backoff is due and the source is still eligible.**
  The sender keeps one pending row per (hub, Memory, record) in `FederationRetry` when the hub's refusal is retryable, and offers it again while its valid pending row is due and the source is still eligible, independent of its sync cursor, so the refusal no longer waits for the row itself to change. A source the sync cursor selects that also has a valid pending row reserves its attempt before the send; a malformed retry row is reported and left as stored. A first non-retryable refusal creates no retry row; an existing pending row becomes terminal, and the retry path in one sender run does not select it again (a later row update can still select it through the ordinary cursor; concurrent sender runs for one peer are not serialized — a separate issue). A due valid pending retry row whose source is deleted or private is recorded as a terminal outcome instead of being offered. The federation sync response also reports whether its SyncLog `put` returned (true) or threw (false, the row's state unconfirmed) (#2797, #2792).
