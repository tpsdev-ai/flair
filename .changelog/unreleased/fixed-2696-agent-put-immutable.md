- **Agent PUT is an administrator operation that updates an existing agent, keeping its stored `createdAt` and `publicKey`; an agent updates its own record with PATCH.** For a request that reaches the Agent PUT handler, a target id outside the agent-id rule is refused 400 before the handler's authorization and existence checks (authentication, routing and Harper's resource admission can refuse earlier); for a valid id, a PUT from any other verified agent is refused 403 (`agent_put_admin_only` when the record exists), and an administrator's PUT to an id with no stored row (and no body `id` that disagrees with the URL's) is refused 404 `agent_put_requires_existing`; `POST /AgentSeed` is a creation path, the one the refusal names, and `POST /Agent/` also creates a row (administrators only). An administrator's PUT is a full replacement: the id comes from the URL (a trusted in-process PUT with no URL target uses its body id), `createdAt`, `publicKey`, `originatorInstanceId` and the receiver federation fields are kept from the stored row, `updatedAt` is set by the handler, and `role` and `admin` are reconciled; every other field comes from the body, so an ordinary field it omits (`status` and `role` included) is not kept. The replacement is built from a re-read of the row in the PUT's own write transaction: a deletion or a key rotation committed after the PUT's first read and before that re-read is seen (a deleted agent is refused with the same 404, a rotated key is kept), and one whose transaction takes its time after the re-read is applied after the PUT's write. For a non-admin PATCH, an admin-status change is decided from the `role` of the row the guard reads and the role that row would have once the body is merged and reconciled; the `admin` mirror is not read as authority, and an administrator's change whose transaction takes its time after that read is applied after the PATCH. A key is rotated by `flair agent rotate-key`, an `update` through Harper's operations API.
