- **The launchd launcher moves aside an `hdb.pid` naming a live process shown not to be Flair, so Flair restarts after pid reuse (flair#2697).**

  After an unclean shutdown, `<ROOTPATH>/hdb.pid` can name a pid the OS has since given to another process, such as a system daemon. At startup Harper reads that pid with `parseInt` and exits 4 (`Harper is already running`) when it is non-zero, is not Harper's own pid or a recognised PID-1 init process, and `process.kill(pid, 0)` succeeds or fails only for lack of permission (a process of another user). launchd's KeepAlive then retried without end and Flair did not come back.

  The launcher now acts only on a positive pid read as Harper reads it (`123junk` is pid 123, `junk123` is no pid). It counts the pid alive as Harper does, including a process of another user. It leaves every other `hdb.pid` to Harper's own check: no digits, zero, a negative value (which Harper passes to `process.kill`, where it names a process group), a file containing a NUL byte, or leading whitespace that is not ASCII.

  It moves `hdb.pid` aside only on positive evidence that the live process is not this instance. Its command line as `ps` reports it must be non-empty and not `node`/`bun` followed by a Harper entry path, and must contain neither `harper` (in any case) nor the data directory. In addition, one of these must hold: the process runs as another user than the launcher; `lsof` is not installed; or `lsof` succeeds with a listing that includes the process's working directory and no open file under the data directory. A failed, killed or empty `lsof` listing counts as no evidence. After the admin-pass checks pass and just before it execs Harper, the launcher links `hdb.pid` to `hdb.pid.stale-<epoch seconds>` (or `.<n>` after it when that name is taken), removes `hdb.pid`, and prints one line naming the pid and the evidence. The link never replaces an existing name. If a file appears at that name meanwhile, the link fails. If a directory appears there, the launcher removes the link `ln` placed inside it, checks the removal, and treats the move as failed. A failed move prints one line, naming any link the launcher could not remove, and execs Harper, which exits 4 if that pid is still alive. Flair does not read the `hdb.pid.stale-*` copies; they are kept for diagnosis and can be deleted.

  In every other case the launcher leaves `hdb.pid` in place, as before. That covers a live process that might be this instance (for example a Harper whose node path contains a space), and any `node`/`bun` process running a Harper entry path. For that last case the flair#2056 refusal (exit 0) still applies when no `flair-daemon.json` sidecar disagrees; otherwise Harper's own check decides. Harper itself is unchanged.
