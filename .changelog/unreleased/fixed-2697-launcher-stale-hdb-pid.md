- **The launchd launcher moves aside an `hdb.pid` naming a live process shown not to be Flair, so Flair restarts after pid reuse (flair#2697).**

  After an unclean shutdown, `<ROOTPATH>/hdb.pid` can name a pid the OS has since given to another process, such as a system daemon. At startup Harper exits 4 (`Harper is already running`) when the pid it reads from `hdb.pid` is alive (including a process of another user), is not its own pid, and is not a recognised PID-1 init process. launchd's KeepAlive then retried without end and Flair did not come back.

  The launcher now reads and judges that pid the way Harper does: `parseInt` of the file (`123junk` is pid 123, `junk123` is no pid; only ASCII whitespace is skipped before the digits, and anything else there leaves the decision to Harper), and alive when `kill -0` succeeds or the process belongs to another user. It moves `hdb.pid` aside only on positive evidence that the live process is not this instance. Its command line as `ps` reports it must be non-empty and not `node`/`bun` followed by a Harper entry path, and must contain neither `harper` (in any case) nor the data directory. When `lsof` is available, the process must also hold no open file under the data directory. After the admin-pass checks pass and just before it execs Harper, the launcher links `hdb.pid` to `hdb.pid.stale-<epoch seconds>` (or `.<n>` after it when that name is taken), then removes `hdb.pid`, and prints one line naming the pid and the evidence. The link fails rather than replace a name that exists by then. If the move fails, the launcher prints one line saying so and execs Harper, which exits 4 if that pid is still alive. Flair does not read the `hdb.pid.stale-*` copies; they are kept for diagnosis and can be deleted.

  In every other case the launcher leaves `hdb.pid` in place, as before. That covers a pid Harper would not count as alive, a live process that might be this instance (for example a Harper whose node path contains a space), and any `node`/`bun` process running a Harper entry path. For that last case the flair#2056 refusal (exit 0) still applies when no `flair-daemon.json` sidecar disagrees; otherwise Harper's own check decides. Harper itself is unchanged.
