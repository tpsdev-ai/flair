- **The launchd launcher moves aside an `hdb.pid` whose live pid is not Harper-shaped, so Flair starts after that pid is reused (flair#2697).**

  After an unclean shutdown, `<ROOTPATH>/hdb.pid` can name a pid the OS has since given to an unrelated process. Harper's own startup check exits 4 (`Harper is already running`) whenever that pid is alive, so launchd's KeepAlive retried without end and Flair did not come back. When `ps` reports a command line for the live pid and it is not `node` or `bun` followed by a Harper entry path (the flair#2056 check), the launcher now renames `hdb.pid` to `hdb.pid.stale-<epoch seconds>` (adding `.<n>` when that name exists; an existing file is never overwritten), prints one line to stderr naming the pid and the reason, and execs Harper. If the rename fails, it prints one line saying so and execs Harper as before. Flair does not read the `hdb.pid.stale-*` copies; they are kept for diagnosis and can be deleted.

  The file is left in place when its pid is dead or unparseable (Harper ignores it), when `ps` reports nothing for the pid, and for any Harper-shaped pid. With no `flair-daemon.json` sidecar or an agreeing one, the launcher still refuses (exit 0, flair#2056). With a disagreeing sidecar, Harper's own check still decides, because Harper's own restart forks a new main process whose pid the sidecar does not name. Harper itself is unchanged.
