- **An auto-promotion whose candidate update throws is reported from the candidate's state at a fresh read, and a later sweep can adopt its recorded memory.** `POST /AutoPromoteCandidates` used to list such a promotion under `promoted` without knowing the candidate's state. After the update throws, the sweep now reads the candidate back. A candidate read back `pending` is listed under a new `incomplete` field as `{ memoryId, candidateId, error }`. One read back promoted on this memory with this reviewer is listed under `promoted`. Any other state, or a failed read, is listed under a new `unconfirmed` field: the promotion on this memory was not confirmed, and `readBack` says what the read found. The read-back establishes only the candidate's state at that moment, not whether this update was the write that produced it. Neither list counts toward `promoted` or `count`. The per-call `limit` now counts every memory write attempt, rejected or thrown attempts included, plus every recorded memory the sweep adopts. A later sweep adopts the memory recorded on a candidate that is still pending when three conditions hold: the memory's identity is present on the candidate, the memory still passes the sweep's identity checks, and it carries the sweep's own approval (`promotionStatus` `approved`, `promotedBy` `machine:adk-auto-promote`, a `promotionContentHash` matching its content, and a `promotedAt`). The sweep re-checks this under the memory's write lock and holds the lock while it updates the candidate. Before this change the sweep wrote a second promoted memory instead. Candidate updates now run in their own transaction. The REM runner records the incomplete and unconfirmed counts on its log row, and `flair rem nightly run-once` prints them on the `Auto-promoted:` line, which now labels the server's skipped count `skipped`. A newly written auto-promoted memory now gets a random id, as `PromoteMemoryCandidate` already does (#2714).
