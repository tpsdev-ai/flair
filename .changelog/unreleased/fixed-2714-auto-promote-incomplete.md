- **An auto-promotion whose candidate update fails is reported from the candidate's confirmed state, and a later sweep can adopt its recorded memory.** `POST /AutoPromoteCandidates` used to list such a promotion under `promoted` while its candidate could still be pending. After the update throws, the sweep now reads the candidate back. A candidate read back `pending` is listed under a new `incomplete` field as `{ memoryId, candidateId, error }`. One read back promoted with this memory and reviewer is listed under `promoted`. When the read fails or finds another state, the promotion is listed under a new `unconfirmed` field with a `readBack` description. Neither list counts toward `promoted` or `count`. The per-call `limit` now counts every memory the sweep writes, whatever the outcome, plus every recorded memory it adopts. A later sweep adopts the memory recorded on a still-pending candidate when the candidate recorded that memory's identity, the memory still passes the sweep's identity checks, and it carries the sweep's own approval: `promotionStatus` `approved`, `promotedBy` `machine:adk-auto-promote`, a `promotionContentHash` matching its content, and a `promotedAt`. The sweep re-checks this under the memory's write lock and holds the lock while it marks the candidate promoted, then reports that memory under `promoted`. Before this change the sweep wrote a second promoted memory instead. Candidate updates now commit in their own transaction. The REM runner records the incomplete and unconfirmed counts on its log row, and `flair rem nightly run-once` prints them on the `Auto-promoted:` line, which now labels the server's skipped count `skipped`. A newly written auto-promoted memory now gets a random id, as `PromoteMemoryCandidate` already does (#2714).
